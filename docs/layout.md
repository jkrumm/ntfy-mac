# Layout

The module map: what each target and folder holds, with its ports and adapters. The dependency direction is in `AGENTS.md` (Architecture and Layout) and enforced in `Package.swift`.

| Path | Purpose |
|-|-|
| `Sources/NtfyCore` | Pure domain and policy, no I/O: messages, priority mapping, errors, config model and token migration, `SettingsCatalog`, `MissedMessagePolicy`, `ReconnectMachine`, `StreamSupervisor`, `DeliveryService` (paced queue, retries, auto-dismiss, re-alert, reminders, boot reconcile, topic settings, quiet hours, `delete`/`deleteAll`), `UIActionCatalog` (History window action to CLI command, rendered in `docs/cli.md`), and the ports (`Clock`, `MessageStream`, `MessagePoller`, `TopicSource`, `CursorStore`, `SystemEvents`, `SecretStore`, `NotificationPoster`, `Delivering`, `HistoryStore`, `HistoryInbox`, `HistoryObserving` (in-process change signal, `ChangeSignal`), `AttachmentFetching`, `ConfigStore`, `NtfyPublishing`, `LoginItemControlling`, `ServerTesting` with `ServerTestResult`), `LegacyInstallCleanup` with `LegacyInstallLayout`/`LegacyCleanupReport` and the ports `LaunchAgentManaging`, `LaunchServicesRegistering`, `LegacyProcessTerminating` (the 1.x leftovers: services, daemon, helper app, Launch Services entries, old binary and logs; `config.json`/`state.json` never touched), and `ServerAddress` (what the user types as a server URL) |
| `Sources/NtfyClient` | HTTP adapters: NDJSON stream, catch-up poller, account topics, image and attachment fetchers (same-origin token, no redirects, size caps; attachments cached under Caches/<bundle>/attachments, pruned after 7 days); `NtfyServerTester` (the connection test for Settings and onboarding); https-only tokens unless `allowInsecure` |
| `Sources/NtfyStore` | History store adapter (GRDB, SQLite WAL, FTS5; topic overview, result counts; a message's `content_type` lives in the JSON payload, so it needed no migration) |
| `Sources/NtfyPlatform` | Keychain, config and 1.x state files (atomic writes), config watcher, wake and path monitor, `os.Logger` helper; the only module that imports UserNotifications: `NotificationCenterClient` (live and fake), `UserNotificationPoster`, `UserNotificationPermissionProvider`, `NotificationResponder`; `SMAppServiceLoginItem` (the app's own login item), `SoundCatalog` (system and user sounds, shared by the CLI and the app), `LegacyInstallCleanup.live` (launchctl, lsregister, process adapters; the app runs it before the pipeline, the CLI as `migrate`) |
| `Sources/NtfyIPC` | Versioned Codable socket protocol (NDJSON); additive commands stay v1 (`delete`: an older app answers `bad-request`, the CLI reports `app-outdated`) |
| `Sources/NtfyAppLogic` | What the app does behind ports, so tests drive it (the app target has no test target): socket request handling (`IPCRequestHandler`, `LocalMessaging`, `PipelineHandles`) and the UI model layer, pure Swift with `Observation` and no SwiftUI/AppKit: `AppModel` (`@MainActor @Observable`: connection summary, unread count, recent rows, pause, permission, actions), `PipelineSource`, `HistoryModel` (the History window: topics, filters with a debounced search, paging, selection that marks read, `MessageDetail`, actions, attachment preview state, export; `apply(selection:)` takes the router handoff), `HistoryExporter` (JSON and CSV), `WindowRouter` (window requests and the History selection), `SettingsModel` (every Settings control writes through `ConfigStore.update` at once; server URL and token go through `ServerConnection`: test, then URL to config and token to the Keychain; `SettingsSection` is the list `exposedSettings` is built from), `OnboardingModel` (three steps), `NotificationPermissionFlow` (state, request under a `QuitGuarding` hold, System Settings deep link, test notification), and the UI ports `SoundListing`, `SoundPreviewing`, `SystemSettingsOpening`, `QuitGuarding` |
| `Sources/NtfyTesting` | In-memory fakes for every port; linked by test targets only |
| `Sources/NtfyMacCLI` | `ntfy-mac` CLI; typed errors map to exit codes only here (0 ok, 1 runtime, 2 usage, 3 auth, 4 app/permission unavailable, 7 server unreachable); `doctor` has a read-only `duplicate-install` check (`DuplicateInstall`: candidate bundles de-duplicated by real path, labelled Homebrew or direct, warns on more than one) |
| `App/` | XcodeGen spec (`project.yml`) and SwiftUI app sources; `App/NtfyMac.xcodeproj` is generated, not committed. `App/Sources` is the app composition root and the only place real adapters meet: `AppController` (config reload, permission, launch) builds and tears down an `AppPipeline` (store, delivery, responses, stream; without a configured server a local one with no stream, so `notify` works before `setup`); `PipelineReload` in the core decides when. It implements `PipelineSource` for the model. UI: `MenuBarExtra` (`.window` style), `Window` scenes for History, Settings and Onboarding (never the `Settings` scene; Settings is `SettingsWindow` with one `Settings*Section` view per `SettingsSection`, Onboarding is `OnboardingWindow` plus `OnboardingSteps`, both over `PermissionStatusView`; the History window is `HistoryWindow` plus `HistorySidebar`/`HistoryList`/`HistoryDetail`/`AttachmentPreview` over `HistoryModel`, `FileQuickLook` isolates `quickLookPreview`, `HistoryFiles` holds the save panels), `WindowCoordinator` (accessory app becomes regular while a window is open), `OnboardingState` (UserDefaults) |
| `docs/cli.md`, `docs/settings.md`, `llms.txt` | Generated from `ntfy-mac schema --json` by `scripts/generate-cli-docs.swift` (`make docs`); never edit by hand. `docs/` also holds `how-it-works.md`, `contributing.md` and `waves/` |
| `tests/<Target>Tests` | Swift Testing suites (`tests/` is lowercase on purpose; the filesystem is case-insensitive) |
| `Sources/NtfyCore/{InstallChannel,UpdateStatus,TeamPin,SigningInspecting}.swift`; `Sources/NtfyPlatform/{CodeSigning,FileTeamPinStore}.swift`; `Sources/NtfyAppLogic/UpdateMenuModel.swift`; `App/Sources/SparkleUpdater.swift`; `Sources/NtfyMacCLI/UpdateCommand.swift` | Updating. The direct channel updates through Sparkle 2 inside the app (EdDSA-signed appcast, feed `https://github.com/jkrumm/ntfy-mac/releases/latest/download/appcast.xml`, key pair in `SUFeedURL`/`SUPublicEDKey` of `App/project.yml`); only the app links Sparkle. `UpdateEligibility` decides whether it runs: a Homebrew formula copy (`InstallChannel`, Cellar or `opt`; the cask copy lives in `/Applications` and is `direct`) never self-updates, nor does a build that is not Developer ID signed, nor `NTFY_MAC_NO_SELF_UPDATE=1`, nor a Team ID that differs from the recorded one. Sparkle cannot pin a Team ID (it accepts an update with a valid EdDSA signature or the same code identity), so the app records the Team ID of its first Developer-ID-signed run (`TeamPinStoring`, file `team-pin` in the app support dir) and `TeamPin` refuses a later mismatch; the publish gate (`scripts/verify-signature.sh`) holds the release to the signing team. Downgrades are refused by Sparkle's version comparison (`CFBundleVersion` is the stamped `x.y.z`). `ntfy-mac update` asks the running app over IPC (`Command.update`, additive v1; `check` probes without UI, otherwise Sparkle's own window opens); a formula copy runs `brew update`, which moves it to the cask. Scheduled finds show as a menu row, never as a window (gentle reminders). Proven on the MacBook 2026-11-14 from 2.0.0 to 2.0.1 against the published appcast (`docs/waves/PLAN.md` Wave 7); the scheduled menu row is not yet seen |
| `scripts/tools.sh` | Pinned, SHA-256-verified tool binaries in `.tools/` (SwiftLint, Periphery, XcodeGen) |
| `scripts/apple-slot.sh` | Wraps every `xcodebuild`: on the mini one Apple job at a time across repos (shared with iris) inside a factory test slot named by `APPLE_SLOT_NAME` (default `ntfy-mac-apple`; `app` sets `ntfy-mac-app`, `snapshots` `ntfy-mac-snapshots`, so the retro can tell them apart); bare in CI and on the MacBook |
| `scripts/sign.sh`, `scripts/verify-signature.sh`, `scripts/apple-credentials.sh`, `scripts/appcast.sh` | Code signing, the single entry point. Default ad-hoc (`make check`, snapshots, CI). `SIGN_IDENTITY=developer-id` signs with the team's Developer ID Application certificate, Hardened Runtime and a secure timestamp, inside out (Sparkle's helpers, the bundled CLI, then the app; never `--deep`); `NOTARIZE=1` submits with `notarytool`, waits and staples (`RESUME_NOTARY_ID=<id>` continues a submission that outlived `NOTARY_TIMEOUT`). Every run ends in `verify-signature.sh` (`--release` also checks the staple and Gatekeeper). Credentials: `APPLE_TEAM_ID`, `ASC_KEY_P8`, `ASC_KEY_ID`, `ASC_ISSUER_ID` from the environment, else `secrets-run` on the mini; the team id never goes into a tracked file. `appcast.sh` runs Sparkle's pinned `generate_appcast` and `sign_update --verify` with the EdDSA key file (`SPARKLE_ED_PRIVATE_KEY` in CI, `~/.local/state/apple-developer/sparkle-ntfy-mac-ed25519.key` on the mini) |
| `scripts/stamp-version.sh`, `scripts/package.sh`, `scripts/render-cask.sh`, `packaging/ntfy-mac.cask.rb.in` | Release build: stamp the version into the working tree, build the tarball, the Sparkle zip (`NtfyMac-<version>.zip`, the app only), `appcast.xml` and `SHA256SUMS` into `dist/` (refuses an app that is not Developer ID signed, notarized and stapled unless `ALLOW_ADHOC=1`, which writes no appcast), render the Homebrew cask (url = the zip, sha256 of the zip) from the template |
| `install.sh`, `scripts/test-install.sh` | The curl installer (checksum-verified, Developer ID + Hardened Runtime + stapled + Gatekeeper checked, atomic; `NTFY_MAC_ALLOW_UNNOTARIZED=1` skips those checks for tests and only with a `file://`/local base URL; runs `migrate` before relinking the CLI; `NTFY_MAC_BASE_URL` only accepts `file://` and local http; refuses with exit 1 when a Homebrew formula or cask copy exists (`Caskroom/ntfy-mac` or the `opt` link), `NTFY_MAC_BREW_PREFIXES` overrides the prefixes for tests only, no override flag) and its test against a fake release (`make installer-check`) |
| `scripts/check-commit-msg.sh` | The local commit-msg hook (lefthook): conventional header, 100-character lines |
| `scripts/clean-machine/`, `docs/clean-machine.md` | The clean-machine matrix: `matrix.sh run <15|26|all> [cell...]` installs and upgrades the direct download and the Homebrew cask, alone and together, in fresh macOS guests (Lima, Apple IPSW, one APFS clone per cell, deleted after it) and writes one log per cell with `CHECK ok/FAIL/NOTE` lines. Inside the Apple slot, one macOS at a time, refuses to start a VM below 40 GiB free (the mini panicked at 94% disk). A guest cannot click, so the notification permission ends `denied` there; `macbook-state.sh` is the read-only snapshot for the owner's real Mac. Not part of `make check`; shellcheck covers its scripts. Rerun it after a change to `install.sh`, the cask or the update path; the record is Wave 7 in `docs/waves/PLAN.md` |
